01 · Giới thiệu dự án

Bài toán & mục tiêu

Airline Booking System (ABS) là hệ thống đặt vé máy bay trực tuyến, xây dựng để thực hành thiết kế & triển khai một hệ microservice hoàn chỉnh.

⚡ Đặt vé đồng thời

Đảm bảo một ghế trên một chuyến bay không thể bị nhiều khách đặt cùng lúc, kể cả khi hệ thống nhận hàng trăm request đồng thời vào giờ mở bán.

⏱ Dữ liệu nhạy cảm thời gian

Booking ở trạng thái HELD chỉ giữ ghế 10 phút, tự động giải phóng nếu chưa thanh toán; giá vé biến động theo tỉ lệ ghế đã bán.

04 · Database Design

Database-per-Service

Mỗi service sở hữu 1 database riêng biệt — tham chiếu chéo qua logical FK (BIGINT), không dùng physical foreign key giữa các service.

┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │ flight_db │ │ user_db │ │ booking_db │ │ 6 bảng │ │ 3 bảng │ │ 3 bảng+Redis│ └──────────────┘ └──────────────┘ └──────────────┘ ┌──────────────┐ ┌──────────────┐ │ payment_db │ │ notify_db │ │ 4 bảng │ │ 3 bảng │ └──────────────┘ └──────────────┘ Postgres 16 (1 server, 5 logical DB) Redis 7 (chỉ booking-service — seat-hold lock)
  • booking: HELD → CONFIRMED → CANCELLED / EXPIRED / REFUNDED
  • outbox_event (JSONB) ở booking & payment — at-least-once Kafka delivery
  • @Version trên Flight, SeatInventory, Booking — optimistic locking
  • idempotency_key UNIQUE trên payment — chống double-submit
  • Flyway migration — schema version hoá, rollback được
05 · Giao tiếp giữa services

Sync (REST) + Async (Kafka)

🔗 Synchronous — REST/JSON

Dùng khi caller cần kết quả ngay: booking → flight-search (check ghế), booking → user (validate hành khách) — qua OpenFeign client.

📨 Asynchronous — Apache Kafka

Dùng cho luồng background, nhiều consumer phản ứng cùng lúc: xác nhận booking, gửi email, compensation khi payment fail.

06 · Saga & Outbox

Choreography Saga cho Booking ↔ Payment

Không dùng orchestrator trung tâm — mỗi service tự biết phải làm gì khi nhận event, loose coupling tối đa.

Hold seat (HELD)
→
publish booking.held
→
Payment SUCCESS
→
publish payment.completed
→
booking → CONFIRMED
→
Email xác nhận
Payment FAILED
→
publish payment.failed
→
booking → CANCELLED
→
release seat lock
→
Email báo hủy

Outbox pattern: ghi business write + outbox_event cùng 1 transaction → relay worker poll mỗi 2s → publish Kafka → đảm bảo không mất event kể cả khi Kafka tạm down.

07 · Chống double-booking

2 lớp bảo vệ chồng nhau

1  Redis Distributed Lock

SETNX seat:{flightId}:{seatNo} — TTL 10 phút, atomic, < 1ms latency. Người thắng giữ ghế, người thua nhận 409 Conflict ngay lập tức.

2  DB Optimistic Locking

@Version trên SeatInventory + UNIQUE index (booking_id, seat_no) — lớp bảo vệ backup an toàn tuyệt đối nếu Redis bị flush hoặc mất dữ liệu.

Redis nhanh nhưng không bền vững; DB chậm hơn nhưng chính xác tuyệt đối. Kết hợp cả hai → hiệu năng cao + correctness được đảm bảo.

08 · Resilience & Observability

Tự bảo vệ & khả năng quan sát

🩺 Health Check

/actuator/health ở mỗi service, kiểm tra kết nối DB, Redis, Kafka — cảnh báo khi error rate > 1% hoặc latency p99 > 1s.

📈 Metrics

Micrometer + Actuator → Prometheus scrape → Grafana dashboard: request rate, error rate, latency p50/p95/p99.

🔍 Distributed Tracing

traceId/spanId xuyên 5 service, gửi lên Zipkin — debug 1 lượt booking qua toàn hệ thống dễ dàng.
